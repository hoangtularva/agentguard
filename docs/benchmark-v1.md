# `/v1/check` latency

Generated by `npm run bench:v1` (PGlite) and `npm run bench:v1 -- --pg` (PostgreSQL 16 via embedded-postgres). Raw results: [results/v1-latency-pglite.json](results/v1-latency-pglite.json), [results/v1-latency-postgres16.json](results/v1-latency-postgres16.json).

**Setup.** Client-observed HTTP latency on localhost: the real `/v1` route handlers behind a Node HTTP server, `fetch` from the same process, sequential requests (300 per case after 20 warm-ups), one session with two registered sources. Throughput: 8 concurrent clients on the ALLOW path. Machine: Intel i5-7200U (2 cores / 4 threads), 12 GB RAM, Windows 10, Node 22.

## Baseline (P4.9, before optimisation)

| Case | PGlite p50 / p95 / p99 (ms) | PostgreSQL 16 p50 / p95 / p99 (ms) |
|---|---|---|
| ALLOW (read, issues a decision token) | 28.8 / 44.1 / 65.9 | 20.5 / 31.1 / 42.9 |
| BLOCK (injected destination) | 23.2 / 39.7 / 63.9 | 13.5 / 19.5 / 23.4 |
| REVIEW (creates a bound approval) | 22.2 / 33.3 / 52.3 | 17.6 / 26.2 / 33.0 |
| Throughput, 8 clients | 39 checks/s | 78 checks/s |

The policy decision itself takes microseconds (see the simulated benchmark); the time is spent in ~15 database round trips per check (API key lookup and usage stamp, catalog and session reload, identity verification, policy load, decision row, audit, token). That is the target of optimisation O4 in P4.10, measured again with the same script.

**How to read this.** Numbers are from one laptop and include the HTTP stack; the PGlite figures are a single embedded connection, so concurrency doesn't help there. They are an order of magnitude below a typical LLM turn (seconds), which is the relevant comparison for an agent loop.

## After optimisation O4 (P4.10)

Changes, each removing round trips or blocking work on the hot path: identity verification in one joined query (was 3); active policy in one joined query with the validated document cached per immutable version (was 2 queries + Zod parse); per-app tool catalog and resource labels cached for 5 s and invalidated on tool registration; API-key usage stamp at most once a minute per key (was a write per request); decision-only ALLOW inserted as `allowed` directly (one UPDATE less); the audit-chain sealer writes each batch in one statement, so it holds its lock briefly (on PGlite the per-row version caused ~200 ms p99 spikes).

| Case | PGlite p50 / p95 / p99 (ms) | PostgreSQL 16 p50 / p95 / p99 (ms) |
|---|---|---|
| ALLOW | 18.0 / 24.3 / 52.2 (was 28.8 / 44.1 / 65.9) | 17.8 / 31.5 / 50.5 (was 20.5 / 31.1 / 42.9) |
| BLOCK | 15.9 / 36.6 / 82.7 (was 23.2 / 39.7 / 63.9) | 13.8 / 20.1 / 28.4 (was 13.5 / 19.5 / 23.4) |
| REVIEW | 18.4 / 38.4 / 67.6 (was 22.2 / 33.3 / 52.3) | 14.2 / 18.6 / 22.0 (was 17.6 / 26.2 / 33.0) |
| Throughput, 8 clients | 63 checks/s (was 39) | 92 checks/s (was 78) |

Honest reading: medians improved 15–37 % on PGlite and 0–19 % on PostgreSQL; throughput +62 % / +18 %. Tails on a shared laptop are noisy (the Docker stack was running during these runs), and the BLOCK path on PostgreSQL did not change measurably. The remaining cost is the writes every decision must make (decision row + audit event; token or approval). No indexes were added: the dashboard perf test (O5) still shows no need.
